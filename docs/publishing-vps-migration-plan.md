# Showwork: Netlify website + existing InterServer VPS workers

Status: design only; production NO-GO. No deployment, credentials, VPS login, database connection or live configuration changes were performed. This replaces the proposed paid hosted-staging direction. No new paid services are required by this design; feasibility depends on the existing VPS and account allowances.

## Plain-language architecture

Netlify continues serving the website, dashboard, login, publishing settings and OAuth callbacks. The user schedules a post in the dashboard; the authenticated application saves that intention in Supabase. A continuously running VPS worker finds due work, claims it exclusively, publishes through the platform API and saves the result. The dashboard reads those results as it does today.

Supabase remains the shared source of truth. Do not move the production database to the VPS. Do not have the VPS call Showwork's cron API once a minute: that would retain unnecessary Netlify invocations. A durable database queue is sufficient; no paid Redis, message broker or new hosting project is needed. The VPS does not need a public worker HTTP endpoint. It initiates outbound database/provider connections.

## VPS requirements: verify before deciding capacity

Suggested starting test capacity, not a proven production minimum: 2 vCPU, 4 GB RAM and at least 20 GB available SSD space for the worker/runtime, logs and bounded temporary media. Video-heavy processing may require 4 vCPU/8 GB or lower concurrency; do not purchase an upgrade without approval. If the existing allocation is smaller, benchmark with one media-processing slot and report whether it meets targets. Do not assume eight network attempt slots means eight simultaneous video conversions.

Use a supported Linux LTS release (Ubuntu 24.04 LTS is a suitable proposed target), a pinned supported Node runtime validated against this app, generated Linux Prisma engine, ffmpeg/ffprobe, CA certificates and reliable UTC time synchronization. Build a worker-only release; no Next.js server, public database or hosting control panel is needed. Confirm architecture, available disk, outbound IPv4/IPv6, DNS, provider access and bandwidth allowance. Run synthetic PostgreSQL/PgBouncer locally on this same VPS during testing, bound to loopback, and remove it afterward. Its CPU/RAM contention means local-DB benchmarks alone do not model remote Supabase latency.

Use systemd for startup on reboot, bounded automatic restarts and graceful SIGTERM handling. Start with one supervised runner containing the admission/recovery loop and bounded consumers; use existing database leadership/epochs even with one machine. Prevent two release versions from running concurrently during upgrades. Restart a consumer/session without losing durable queue state. The current portable consumer has a ten-minute limit, so initially renew sessions inside the long-lived supervisor and test the handoff instead of simply removing the deadline.

Security: dedicated non-root worker user, SSH keys restricted to administrator addresses, firewall with no public worker/database port, patched OS, root-readable credential files supplied securely at service start, no secrets in source/logs/CLI arguments, resource limits and restricted writable temporary directories. Scope storage credentials to necessary publishing media. A real worker must read selected customer post content and social tokens to publish; it is not a read-only diagnostic and must be reviewed accordingly. Do not copy the entire website environment or Supabase administrator/service-role credentials.

Monitoring without a paid service: systemd/journald with retention limits; periodic local health checks; durable heartbeat/job-age/error metrics; disk/RAM/CPU checks; existing approved notification channel for alerts. Never send alert messages without authorization. A monitor on the VPS cannot reliably report total VPS failure: use an existing independent monitor/provider notification if available, or a low-frequency health check from Netlify (e.g. five minutes = 8,640 invocations/30 days if separately scheduled). This is an explicit reliability-versus-usage choice, not an assumed free external service. Backups and restore tests must use storage already included in current accounts; confirm InterServer entitlement rather than purchase backup storage.

## Safe Supabase connection design

Use a dedicated publishing login, no superuser/role creation/schema-management powers; explicit required table/column grants for posts, assets, workspace entitlement checks, connections/token refresh, queue/leases and publication reporting. Audit inherited PUBLIC privileges, functions, schema access and RLS behavior. Existing Prisma queries are not automatically protected by a dashboard user's JWT; application permission checks and database role restrictions both matter. Install schema using a separately authorized migration identity, never the runtime identity.

Require encryption and certificate/hostname verification using the official Supabase CA procedure; never use a TLS verification bypass. Supabase documents different direct/session/transaction connection modes and IPv4/IPv6 behavior. Select the compatible endpoint after checking connectivity; do not buy an IPv4 add-on simply for this migration. See [Supabase connections](https://supabase.com/docs/guides/database/connecting-to-postgres) and [pooling and limits](https://supabase.com/docs/guides/database/connecting-to-postgres/pooling-and-limits).

Keep the publishing backend budget at five, with only three heavy operations concurrently. A local loopback PgBouncer can enforce one database/user aggregate cap with no reserve pool across all VPS worker processes; choose direct or session upstream when available and validate the complete chain. If using Supabase transaction pooling, validate Prisma compatibility and the server-side pool accounting rather than assuming five client sockets guarantees five global database backends. No unpooled publishing side path. Netlify website traffic and remaining jobs also consume Supabase capacity: establish whether the existing five limit is a publishing allocation or the entire shared database allocation before assigning all five to workers. During cutover old/new workers cannot each claim a separate five-connection allowance.

Use short queries, bounded transactions, database-side deadlines and transaction-scoped locks; do not hold a database transaction during remote API/media processing. Preserve shared token-refresh locking and platform/account pacing. Readbacks resolve lost commit acknowledgements. Store provider acceptance/operation IDs durably; TikTok upload acceptance is not confirmed publication. If a request may have reached a provider but its outcome cannot be verified, quarantine it. A machine restart or rollback must never turn uncertainty into a fresh publishing attempt.

Initially retain one-minute admission cadence; add bounded due-aware waiting in the persistent runner after testing so posts just after a tick do not unnecessarily wait a full minute. Empty-queue exponential/bounded backoff limits database polling; it should not be replaced with repeated website requests. Hosting on a VPS removes serverless cold starts/lifetime limits but does not remove Supabase RTT, rate limits or finalization cost. Existing tests passed main attempt-start targets, yet a 1.38-second coordinator latency yielded 120.30 seconds for 50 posts; production speed remains unproven from this VPS.

## Estimated Netlify savings

30-day month, schedules firing continuously, each legacy cron making one self-API request: three crons produce 129,600 scheduled executions plus approximately 129,600 Next.js API invocations = **259,200 invocations/month removed** when both layers retire. This is a topology estimate, not a measured bill: it exceeds the cited 145,252 count and must be reconciled with deployment dates, dashboards, failed dispatches and actual accounting.

If the deployed baseline were already the direct consolidated candidate, removing it saves only **43,200 scheduled executions/month**, not 259,200. Each scheduled background publishing attempt moved to VPS removes roughly one additional `publish-post-background` invocation, plus any retries previously billed. Do not double-count its HTTP request as another Next.js API invocation. Daily reporting move would remove approximately 60 more invocations/month (30 cron + 30 API) plus dashboard-triggered background syncs. Website/dashboard/API/auth activity, unrelated crons and frontend polling remain. Optional monitoring requests must be subtracted from savings. Supabase and social API traffic still exists; CPU/network work has moved, not vanished.

## Safe migration stages — each production action requires approval

1. Inventory only: obtain non-secret VPS specifications/region and Supabase region/pool allocation; compare repository with an authorized deployed-function inventory. No production credentials needed for this planning step.
2. Offline implementation: worker-only build, systemd unit, database configuration validation, queue-aware user-action integration, explicit ownership routing/kill switch and reviewable migrations. No deploy yet.
3. After explicit permission to configure the existing VPS, run only synthetic tests there: local PostgreSQL/PgBouncer capped at five, mocked providers, normal/50/250 bursts and continuous arrivals, realistic latency injection, media load, reboot, SIGKILL, timeout, disk pressure and stale-leader scenarios. Verify one publish attempt, observable failures/quarantines and complete accounting for every admitted job. Record p50/p95/max attempt and confirmation delays separately.
4. After a separate authorized production-connectivity stage, verify least-privilege access and actual VPS-to-Supabase latency using predefined minimally invasive queries. This is not authorized now. No real publishing during this stage. Obtain final production migration approval only after performance/recovery/security gates pass.
5. Gradual cutover requires **both old and new paths to enforce a common account/cohort ownership gate**. Existing legacy workers do not automatically honor the new queue leases. If that gate cannot be implemented and tested, use a scheduled stop-and-drain cutover instead of running both systems. Select an explicitly approved small account cohort; remaining accounts stay old-owned. Partition the existing five-connection budget rather than doubling it.
6. Stop old admissions for the selected cohort, drain recent started jobs, disable/fence delayed legacy envelopes and stale API dispatch. Import only verified legacy state through the reviewed recovery bridge. Keep accepted TikTok IDs on status-only recovery, confirmed proof on finalization-only recovery and ambiguous jobs in quarantine. Enable VPS ownership atomically only when old senders cannot execute. Expand by account after measured checks; all five platforms must be represented before full cutover.
7. Once stable and approved, remove old scheduled functions from the deployment artifact and verify the deployed list/absence of invocations; source deletion alone is not enough. Retain necessary recovery evidence. Disable only publishing-specific legacy routes/gates; do not rotate the shared CRON_SECRET and break unrelated jobs. Consider daily analytics migration separately.

Rollback: stop new VPS admissions/sends, retain durable state, drain or classify in-flight work, fence its owner epoch and only then transfer verified unsent jobs back. Never simply re-enable the old crons or reset PUBLISHING/unknown jobs to SCHEDULED. The old worker cannot necessarily interpret new durable proof; a tested backward handoff or recovery-compatible previous worker release is required. Confirmed/accepted/uncertain work stays on reconciliation/quarantine paths. Keep the VPS service disabled, not erase its queue. Rollback preserves database records, evidence and token updates.

Potential extra usage includes Supabase compute/egress, existing media-storage requests/egress, VPS transfer, backup space and social API quotas.
